## 001 — Backend: Python + FastAPI
- **Why:** Role is Python/React/AI; FastAPI gives typed request
  validation (Pydantic) and auto-generated API docs.
- **Alternatives:** Django (heavier than needed), Node (off-role).

## 002 — Database: SQLite locally & in tests, Postgres in deployment
- **Why:** SQLite is zero-setup and fast for tests; free hosts wipe
  local files on restart, so the deployed app uses hosted Postgres.
  SQLAlchemy makes the switch a connection-string change.
- **Trade-off:** Minor SQLite/Postgres behaviour differences
  (e.g. case-sensitive search) — covered by testing key queries.

## 003 — Salaries stored in local currency, no FX conversion
- **Why:** Within-country comparison is accurate; FX adds rate-source
  and date decisions. *(Pending Incubyte's answer to Q1)*

## 004 — UI components: MUI + MUI X DataGrid (free)
- **Why:** The employee table needs server-side pagination, sorting and
  filtering over 10,000 rows; DataGrid's server mode handles this with
  minimal custom code.
- **Alternatives:** shadcn/ui + TanStack Table (more control, more code).
- **Trade-off:** Heavier bundle, more generic look.

## 005 — Python packages: uv
- **Why:** Lockfile (`uv.lock`) gives reproducible installs across
  machines and deployment; manages the virtual environment automatically.
- **Alternatives:** pip + venv with pinned requirements.txt (familiar,
  but lockfile management is manual).
- **Trade-off:** Small learning curve.

## 006 — Global styles: MUI CssBaseline, no custom CSS
- **Why:** Template demo CSS removed; CssBaseline is MUI's standard
  browser-style reset, keeping all styling in one system.
- **Trade-off:** Small bundle increase; negligible at this stage.

## 007 — Frontend linter: oxlint (template default)
- **Why:** Ships with the current Vite react-ts template; fast, zero
  configuration needed for this project's size.
- **Alternatives:** ESLint (more plugins and rules, more setup).

## 008 — Schema: SQLAlchemy create_all, no migrations tool
- **Why:** Demo data is regenerated by the seed script; no production
  data to migrate. Avoids Alembic setup for no current benefit.
- **Trade-off:** Alembic would be required before holding real data.

## 009 — Currency derived from country, not user input
- **Why:** Guarantees one currency per country, so per-country salary
  statistics never mix currencies.
- **Trade-off:** Cannot represent employees paid in a foreign currency
  (e.g. expats). Acceptable for this scope.

## 010 — Salary stored as integer (whole currency units)
- **Why:** Floats cannot represent money exactly; annual salaries don't
  need minor units, and some currencies (e.g. JPY) have none.
- **Trade-off:** No fractional amounts; revisit if monthly or hourly
  pay is introduced.

## 011 — Employee list: offset pagination, filters, case-insensitive search
- **Pagination:** `page` + `page_size` (default 20, max 100), ordered by
  `id` so results are deterministic. Response includes `total` for the
  table's page count.
- **Filters:** exact match on country, department, job title; name search
  is case-insensitive substring match (`ilike`), which behaves the same
  on SQLite and Postgres (plain `LIKE` does not).
- **Indexes:** on country, department and job_title, the filtered columns.
- **Trade-off:** Offset pagination slows on very deep pages at large
  scale; fine at 10,000 rows. Keyset pagination would be the upgrade path.

## 012 — Read, update, delete: GET / PATCH / DELETE /employees/{id}
- **PATCH, not PUT:** HR edits usually change one field (most often
  salary); partial updates avoid resending the whole record.
- **Same rules as create:** salary > 0, hire date not in the future,
  valid email, unique email (409). Changing country re-derives currency,
  so decision 009 holds on update too.
- **Hard delete, returns 204.** Unknown id returns 404 on all three.
- **Trade-off:** No audit trail of past values or deletions; salary
  history is out of scope pending Incubyte's answer (Q5).

## 013 — Seed data: deterministic generator, standard library, bulk insert
- **Design:** pure `generate_employees(count, seed)` (no database) plus a
  CLI script that clears the table and bulk-inserts in one transaction.
- **Deterministic:** fixed seed, same 10,000 employees every run; tests
  use small counts.
- **No Faker:** curated name lists per country using Python's `random`;
  one less dependency. Trade-off: less name variety.
- **Realistic pay:** base salary per job title per country (local
  currency) with a random spread, so insights show real patterns. Base
  figures are illustrative, not market data.
- **Target:** full seed in under 5 seconds.

## 014 — Insights: salary statistics per country and per job title
- **Endpoints:** `GET /insights/countries` (headcount, min, max, mean,
  median per country) and `GET /insights/countries/{country}/job-titles`
  (same statistics per job title within one country). All figures in
  local currency; no cross-country totals (decision 009).
- **Full-time only by default:** part-time pay is pro-rated, so mixing it
  in skews averages. An `employment_type` query parameter overrides.
- **Median alongside mean:** salaries are skewed by high earners; median
  shows typical pay more honestly.
- **Median computed in Python** (`statistics.median`): SQLite has no
  median function; this keeps one code path for SQLite and Postgres.
  Loads only the salary column, never full employee records, so it
  stays within the spirit of the "never load all employees" rule.
- **Trade-off:** at much larger scale, use Postgres `percentile_cont`.
